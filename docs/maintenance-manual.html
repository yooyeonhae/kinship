이 앱을 처음 여는 사람을 위한 정비 매뉴얼

맞벌이 가족의 아침을 돕는 웹앱입니다. 이 문서는 어떤 화면이 있고, 그 화면이 무엇을 건드리며, 고칠 때 무엇을 조심해야 하는지를 그림으로 먼저 보여줍니다. 코드를 한 줄도 읽지 않은 사람이 이 문서만 보고 “어디를 열어야 하는지” 찾을 수 있는 것이 목표입니다.

전체 구조 3개의 조각

움직이는 부품은 세 개뿐입니다. 브라우저에서 도는 화면, 데이터를 지키는 Supabase, 그리고 외부 API 키를 감추기 위한 작은 서버 함수. 서버에서 돌아가는 우리 코드는 마지막 하나가 전부입니다.

먼저 알아야 할 것 — 이 저장소에는 앱이 두 벌 있습니다

app/ 이 지금 쓰는 React 버전이고, screens/ 는 예전 정적 HTML 버전(localStorage로만 동작)입니다. 둘은 일부러 따로 갑니다. 고칠 곳은 거의 항상 app/ 입니다.

화면 지도 app/src/pages

주소 하나에 화면 파일 하나가 붙습니다. 누가 들어갈 수 있는지는 app/src/App.jsx의 문지기(가드)가 정하고, 못 들어가면 조용히 다른 화면으로 보냅니다.

ChatBot

규칙 기반 한국어 해석기(LLM 아님). 할일 추가·완료·조회와 옷차림 질문을 처리합니다. 아이가 쓰면 자기 할일만 넣도록 서버가 강제합니다.

각각 보상 목표, 오늘 일정 + 알림 예약, 퇴근길 저장함. 화면 안에 끼워 쓰는 부품입니다.

신원과 권한 로그인이 없다

이 앱에는 로그인이 없습니다. 대신 요청마다 헤더 세 개가 실려 나가고, 데이터베이스가 그 값을 보고 “이 사람이 이 행을 봐도 되는가”를 판단합니다. 무엇을 보장하고 무엇을 못 하는지가 분명하니, 발표에서 넘겨 말하지 마세요.

데이터 모델 가족이 모든 것의 뿌리

모든 표가 family_id를 갖고, 그 값이 곧 울타리입니다. 표를 새로 만들 때도 이 칼럼과 RLS 정책을 빠뜨리면 안 됩니다 — 빠뜨리면 남의 가족 데이터가 보입니다.

할일과 별 가장 자주 오해하는 부분

저금통이 두 개입니다. 아이의 별과 가족의 포인트는 서로 다른 규칙으로 쌓이고, 서로 다른 보상으로 갑니다. 여기를 헷갈리면 점수가 이상해집니다.

연속 달성(스트릭)은 ‘완료’ 기준

부모가 이틀 뒤에 확인해도 아이의 연속이 깨지면 안 됩니다. 아이가 한 일은 그날 한 것이니까요. 할일이 하나도 없던 날은 건너뛰고, 오늘이 아직 안 끝났으면 끊지 않습니다.

저장하지 않고 매번 계산합니다(computeStreak) — 따로 저장하면 할일을 지웠을 때 기록만 남아 어긋납니다.

별은 ‘승인’ 기준

체크는 아이가 혼자 누르는 것이라, 실제로 했는지는 아이만 압니다. 별은 보상으로 바뀌는 값이라 확인하는 사람이 필요합니다. 그 확인이 곧 “봤다”는 신호가 되어 아이에게 전해집니다.

완료를 풀면 서버가 도장도 함께 뗍니다 — 안 그러면 껐다 켜기로 확인받지 않은 별이 되살아납니다.

아지트의 실시간 조합이 특이하다

Supabase의 실시간 기능 중 Broadcast와 Presence만 씁니다. 표 변경 감지 (postgres_changes)는 이 앱에서 동작하지 않습니다 — 신원이 요청 헤더에만 실리는데, 그 방식은 웹소켓의 토큰으로 권한을 따지기 때문입니다.

미니게임을 추가할 때

game_key를 검사하는 CHECK 제약이 두 곳(game_results, game_sessions)에 있습니다. 한쪽만 넓히면 “혼자서는 되는데 원격만 안 된다”로 보입니다.

외부 API app/api

브라우저에서 바로 부르지 않는 이유는 두 가지입니다 — 키가 번들에 박히고, CORS에 막힙니다. 그래서 작은 서버 함수를 두고 그 뒤에서 키를 붙입니다. 키는 app/.env에 VITE_ 접두사 없이 넣습니다. 붙이면 브라우저로 새어 나갑니다.

파일부르는 곳주의할 점
api/tour.js주말 나들이국문 서비스를 써야 결과가 나온다. 축제는 종료일을 직접 걸러낸다
api/weather.js아이 옷차림기상청이 아니라 OpenWeatherMap. 눈에는 우비를 권하지 않는다
api/news.js정보 피드—
api/linkmeta.js퇴근길 저장함키가 없는데도 프록시를 쓰는 유일한 경우(CORS). 쇼핑몰은 제목을 안 주는 게 정상
api/push.js가족톡 알림서비스 롤 키를 쓰지 않는다 — 뚫리면 DB 전체가 열린다

배포할 때는 Vercel 프로젝트의 환경변수에도 같은 이름으로 넣어야 합니다. 로컬에서는 npm run dev가 같은 /api/* 경로를 그대로 띄워 주므로 따로 준비할 것이 없습니다.

고치는 순서 이 순서를 지키면 안 깨진다

데이터 구조가 바뀌는 작업은 항상 데이터베이스가 먼저입니다. 화면부터 고치면 화면은 멀쩡한데 저장만 실패합니다.

  1. 바꿀 것이 표나 권한인지 먼저 판단합니다. 칼럼·정책·RPC가 필요하면 app/supabase/에 migration_NN_이름.sql 파일을 새로 만듭니다. 기존 파일은 고치지 않습니다 — 이미 실행된 것이라 고쳐도 반영되지 않습니다.
  2. Supabase 대시보드의 SQL Editor에서 실행합니다. 이 환경에는 Supabase CLI도 psql도 없고, 익명 키로는 정책을 만들 수 없습니다. 사람이 붙여넣어 실행하는 것이 유일한 길입니다.
  3. 화면을 고칩니다. 규칙(계산·판정)은 app/src/lib/에, 화면은 app/src/pages/에 둡니다. 규칙을 화면 안에 적으면 다른 화면에서 같은 값이 어긋납니다.
  4. 검증합니다. npm run build(문법·임포트)와 npm run lint. FamilyContext.jsx의 경고 한 줄은 원래 있는 것이라 무시합니다.
  5. 권한과 정책은 curl로 확인합니다. 화면을 클릭해 보는 것보다 훨씬 빠르고, 정책이 실제로 어떻게 동작하는지 알 수 있는 유일한 방법입니다.
    상태 코드를 믿지 마세요 — 가족 id가 틀리면 오류 없이 200 []이고, 한 행도 지우지 못한 삭제도 204입니다. 결과 행을 직접 확인해야 합니다.
  6. 눈으로 봐야 하는 것은 브라우저에서 봅니다. 애니메이션, 진행 막대, 배치는 빌드도 린트도 잡아주지 않습니다.

함정 모음 전부 실제로 겪은 것

원인을 찾는 데 가장 오래 걸렸던 것들입니다. 증상이 비슷하면 여기부터 보세요.

고쳤는데 안 고쳐진다

증상: 코드는 분명히 바꿨는데 화면이 그대로다.

개발 서버가 두 개 떠 있습니다. 예전 서버가 5173을 물고 있으면 새 서버는 5174로 밀려나고, 우리가 보는 5173은 계속 수정 전 코드입니다. netstat -ano | grep ':517'로 확인하고 정리한 뒤 다시 띄우세요.

가족을 만들면 42501로 실패한다

증상: 온보딩에서 가족 생성이 권한 오류로 롤백된다.

families에 넣을 때 .select()를 붙이면 안 됩니다. 붙이면 방금 넣은 행을 다시 읽으려 하고, 그 읽기가 조회 정책에 걸려 넣기까지 통째로 취소됩니다. id는 클라이언트가 만들어 헤더와 같은 값을 써야 합니다.

실시간이 오류 없이 조용히 안 온다

증상: 표는 잘 바뀌는데 다른 기기 화면이 갱신되지 않는다. 오류도 없다.

표 변경 감지(postgres_changes)를 쓴 것입니다. 이 앱의 신원은 요청 헤더에만 있어서 그 방식은 한 행도 전달하지 않습니다. Broadcast로 바꾸세요.

아침에 넣은 할일이 ‘지난 일’로 들어간다

증상: 새벽~오전에 추가한 항목이 오늘이 아니라 지난 날짜로 분류된다.

데이터베이스는 UTC로 돕니다. 한국 시간 자정~오전 9시 사이에는 서버의 “오늘”이 하루 이릅니다. 날짜를 만들 때는 current_date가 아니라 서울 기준 함수(app_today())를 쓰세요.

원격 대전이 느리고 자주 실패한다

증상: 한 수를 두면 저장 요청이 끝없이 반복된다.

올린 뒤 돌아온 판은 내용이 같아도 다른 객체라, 참조로 비교하면 늘 “바뀌었다”가 됩니다. 판 내용의 서명(문자열)으로 비교해야 합니다.

점수가 계속 늘어난다

증상: 체크를 껐다 켜는 것만으로 포인트가 쌓인다.

완료를 사건으로 적립했기 때문입니다. 점수는 항상 지금 상태에서 세야 합니다. 그러면 체크를 풀 때 점수도 함께 돌아갑니다.
